## Что переносится

`inventory-20261029.json` содержит пути, точные идентификаторы образов и томов.
Переносятся фактические файлы сервера, включая локальные изменения и ignored
assets, исходные `.env`, все базы, Redis и TLS-хранилище Caddy. Секреты не
попадают в этот репозиторий и передаются только по SSH.

Финальный снимок создаётся после включения maintenance и остановки всех
четырёх приложений. SQLite переносится целыми томами после остановки писателей,
PostgreSQL — через `pg_dump -Fc`, Redis — через явный `SAVE`. Очередь Redis
восстанавливается до старта единственного нового worker с Beat.

Снимок на старом сервере: `/root/ms_scanner_migration/final-20261029`.
На новом: `/var/lib/skandata-migration/final-20261029` (root only).
Там лежат SHA256SUMS, исходная конфигурация Caddy, контрольные количества строк
и время остановки/создания снимка. Это снимок на момент переноса, а не текущая
резервная копия после возобновления работы.

## Скрипты

Скрипты предназначены для этого переноса, не являются повторяемым деплоем:

- `bootstrap-new.sh` — подготовка пустого Ubuntu-сервера и Docker.
- `prepare-images.py` — проверка живых image IDs; `--execute` передаёт образы.
- `ssh-pipe.py` — двоичный поток между двумя SSH без локального сохранения.
- `final-snapshot-old.sh` — закрывает доступ, останавливает приложения и снимает данные.
- `restore-new.sh` — одноразовое восстановление на пустой Docker-host, проверка
  checksum, SQLite integrity и количеств записей до запуска приложений.
- `verify-encryption.py` — запускается внутри backend, проверяет расшифрование
  восстановленных токенов, выводит только количество.
- `check-endpoints.py --ip 37.18.102.53` — проверка всех трёх health endpoints
  с настоящими доменами, SNI и проверкой TLS; старый прокси проверяется с его IP.
- `verify-websocket.py` — upgrade и ping/pong через публичный домен без
  привязки к существующему пользователю и без записи в БД.
- `promote-old-proxy.sh` — проверяет новый HTTPS, включает обычный HTTPS-прокси
  на старом сервере и отключает автозапуск старых приложений.

Compose overrides фиксируют исходные образы на время восстановления. На новом
сервере они сохранены в `/home/skand/skandata-migration`. Redis использует
постоянный именованный том `ms_scanner_redis_data`; это закреплено также в
основном `docker-compose.prod.yml`.

## Дальнейшее обслуживание

Пути проектов остаются прежними. Для сканера выполнять деплой на новом сервере:

```bash
ssh skand@37.18.102.53
sudo -i
cd /root/ms_scanner
git pull --ff-only origin main
docker compose -p ms_scanner -f docker-compose.prod.yml build backend worker frontend
docker compose -p ms_scanner -f docker-compose.prod.yml run --rm backend alembic upgrade head
docker compose -p ms_scanner -f docker-compose.prod.yml up -d backend worker frontend
```

Конфигурация Caddy на сервере включает оба виджета и отличается от базовой
конфигурации Git. Сохранять её при обновлениях. Рабочие образы дополнительно
помечены обычными Compose-именами для штатных команд обслуживания.

Для сверки: `/opt/ms_sverka`, `--env-file .env.vendor`, проект `ms_sverka`,
`docker-compose.pilot.yml`, переменная
`SKANDATA_DOCKER_NETWORK=ms_scanner_default`.
Для импорта отгрузок: `/opt/ms_zakaz`, `--env-file .env.vendor`, проект `ms_zakaz`,
оба файла `docker-compose.yml` и `docker-compose.vendor.yml`.
Обновлять их отдельно; это самостоятельные проекты без Git checkout.

## Возврат при проблемах

До открытия доступа на новый сервер можно вернуть старый Caddy из
`Caddyfile.production.before` (писать в существующий файл, сохраняя inode bind
mount), перезагрузить Caddy и запустить старые приложения.

После возобновления записи на новом сервере нельзя возвращать трафик на старую
базу: появятся две расходящиеся копии. DNS на старый IP безопасен только пока
он работает как прокси к новому серверу. Полный возврат требует новой паузы
записи и обратного переноса актуальных данных. Сохранённый старый снимок не
содержит изменений после переключения.
